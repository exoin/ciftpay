# ADR-0006: OpenAPI-first contract in `api/openapi.yaml`

## Status

Accepted — 2026-09-02

## Context

CiftPay has one backend (Go, `cmd/api`) and several consumers: the Next.js merchant/accountant/admin PWA, the public receipt page, the Phase 3 public API for POS and accounting integrations, and inbound webhooks from Daraja and Africa's Talking. Two languages share the same data shapes (invoice states, tax categories, money as integer cents), and the frontend and backend are usually built in separate sessions by an agent that cannot see the other side's code.

Without a shared contract the usual failures appear: the web client guesses field names, error shapes differ between endpoints, and the docs drift from the implementation. The contract also has to be readable by external integrators and by KRA-approved vendors reviewing how CiftPay exposes fiscal data.

## Decision

`api/openapi.yaml` (OpenAPI 3.1) is the single source of truth for the v1 HTTP contract. Code follows the spec, never the reverse.

- **Spec ownership**: every endpoint, request/response schema, enum (`InvoiceState`, `TaxCategory`, `ShortcodeType`, `PaymentStatus`) and security scheme is declared in `api/openapi.yaml` first. A PR that changes an endpoint changes the YAML in the same commit.
- **Web client**: generated by `openapi-typescript` into `web/src/lib/api/schema.d.ts` and consumed through `openapi-fetch` (`web/src/lib/api/client.ts`). `make gen` (target `gen-api`, wrapping `npm run gen:api`) regenerates it; generated output is committed so `web` builds without the toolchain. CI fails if regeneration produces a diff.
- **Go handlers**: hand-written with chi against the spec. Request and response structs live next to the handlers in `internal/<domain>/handler.go` and mirror the YAML component names. A CI drift check (validating live routes and JSON shapes against the spec) is recorded as future work in `plan.md`; until then the review checklist requires the YAML and handler to be changed together.
- **Error envelope**: every non-2xx response uses one shape:

  ```json
  { "error": { "code": "invoice_not_found", "message": "Invoice does not exist", "details": { "id": "…" } } }
  ```

  `code` is a stable, snake_case machine identifier; `message` is English and safe to show to a user; `details` is optional and structured. Validation errors use `code: "validation_failed"` with a `details.fields` map. Webhook endpoints return the exact bodies Daraja expects (`ResultCode`/`ResultDesc`) instead of this envelope.
- **Auth in the spec**: `cookieAuth` (HttpOnly session) for merchant/accountant/admin endpoints, `webhookToken` (path token) for Daraja callbacks, no security for `GET /r/{code}` and `GET /healthz`. Mutations require the CSRF header documented on the security scheme.
- **Versioning**: paths are served under `/v1`. Breaking changes mean a new version prefix and a new spec file; additive changes (new optional fields, new endpoints) stay in v1.
- `docs/api.md` explains how to read and edit the spec; the spec itself is served by the api at `GET /v1/openapi.yaml` for integrators.

## Consequences

### Positive

- One artefact describes the contract for Go, TypeScript, external integrators and reviewers; the agent building the PWA needs only the YAML to work.
- Enum values (invoice states, tax categories) and money-as-cents conventions are typed on both sides; a typo becomes a compile error in the web build.
- The error envelope is consistent, so the PWA has one error component and the Swahili/English microcopy can be keyed on `error.code`.
- Public receipt and Phase 3 public API can be documented by serving the same file; no separate API docs to maintain.

### Negative

- Two places must move together (YAML and Go handler) until the drift check exists; discipline in review is required.
- Hand-written handlers duplicate some struct definitions that a server generator would produce.
- Generated TypeScript in version control creates noisy diffs when the spec changes.
- OpenAPI describes shapes, not semantics; state-machine rules and idempotency behaviour still have to be written in `docs/api.md` and `docs/architecture.md`.

## Alternatives considered

### Code-first with a generated spec (swag/annotations)

Keeps a single Go source of truth. Rejected: the spec becomes a by-product that lags behind, annotations are hard to review, and the frontend agent cannot start until the Go code exists.

### Server code generation with `oapi-codegen`

Would remove the handler drift risk by generating chi stubs from the YAML. Deferred rather than rejected: the generated interfaces constrain middleware and RLS transaction handling (ADR-0007) in ways that are awkward at Phase 0. It is the natural implementation of the "drift check" future work and may be adopted by a later ADR.

### gRPC + grpc-gateway

Strong typing and streaming. Rejected: the consumers are browsers, Daraja webhooks and small POS vendors; JSON over HTTP with a readable YAML contract is the lowest-friction interface for Kenyan integrators.
